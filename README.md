## About

I build and operate the systems a company actually runs on — CRM platforms, integrations, web frontends and the automation layer that ties them together.

My work sits at the intersection of three disciplines: **enterprise platform engineering** on Salesforce (Apex, Lightning Web Components, Flow, deployment pipelines against a live production org), **full stack web development** with more than ten years of shipping performant, user-centered interfaces, and **AI engineering** — putting large language models into production workflows through APIs, named credentials, guardrails and purpose-built MCP tooling.

I think in products, not tickets. Every integration I ship is designed for the operator using it: bulk-safe, observable, reversible, and documented well enough that the next person does not have to reverse-engineer it. I care about the unglamorous parts — field-level security, rollback plans, idempotent syncs, rate limits on anything that costs tokens — because that is what separates a demo from a system people trust on a Monday morning.

## Featured Projects

<details>
<summary><b>WPTrustRocket</b> — Trusted Shops review engine for WordPress</summary>

<br/>

A production WordPress plugin that pulls customer reviews from the Trusted Shops eTrusted API, stores them locally, and renders them anywhere on the site — via shortcode, native Oxygen Builder elements or a REST endpoint.

| | |
|---|---|
| **Stack** | PHP 7.4+, WordPress 5.8+, OAuth2, WP-Cron, REST API, CSS Custom Properties, Oxygen Builder |
| **Scale** | Full paginated sync of the entire review history into a dedicated database table; review grouping and curation on top |
| **Performance** | Cron-driven synchronisation instead of request-time API calls; four render layouts (grid, slider, list, badge) with real-time touch handling and edge resistance |
| **Security** | OAuth2 client-credentials flow, credentials held in WordPress options, complete uninstall routine removing tables, options and cron jobs |
| **Impact** | Automatic JSON-LD `AggregateRating` markup for rich snippets; review presentation fully themeable without touching plugin code |
| **Repository** | [MGue95/wptrustrocket](https://github.com/MGue95/wptrustrocket) |

The plugin was built because the vendor widget was neither themeable nor curatable. Owning the data locally turned reviews into a first-class content type: editors group and select them, designers style them through CSS custom properties, and search engines get structured markup — with a single OAuth sync job as the only moving part.

</details>

<details>
<summary><b>3CX MCP Server</b> — LLM tooling for enterprise telephony</summary>

<br/>

A Model Context Protocol server that exposes a 3CX V20 phone system to LLM agents: users, extensions, registration state, call history, queues, ring groups, trunks, phonebook and forwarding profiles.

| | |
|---|---|
| **Stack** | TypeScript, `@modelcontextprotocol/sdk`, Zod, Node.js 20+, 3CX XAPI (Configuration + ReportCallLogData) |
| **Scale** | 22 typed tools spanning read and write operations across the entire PBX configuration surface |
| **Performance** | Thin API layer with schema-validated inputs; call history served from the CDR reporting endpoint rather than paged config calls |
| **Security** | Credentials injected via environment, write operations (create / update / delete / forwarding) explicitly gated behind operator confirmation |
| **Impact** | Turns "who missed calls today?" and "set extension 101 to away" into direct conversational operations for support and MSP teams |
| **Repository** | `Private` — available on request |

The design principle was that an agent should never be able to reconfigure a phone system by accident. Every destructive tool requires the numeric object ID retrieved through a preceding read call, and the server instructions push the model to confirm before writing.

</details>

<details>
<summary><b>Enterprise Salesforce Platform</b> — CRM engineering in production</summary>

<br/>

Ongoing platform engineering on a live Salesforce production org: custom Lightning Web Components, Apex services, automated flows, permission architecture and deployment tooling — no sandbox safety net, so everything ships validated.

| | |
|---|---|
| **Stack** | Apex, Lightning Web Components, Flow, SOQL, Platform Events, Named Credentials, Salesforce CLI, GitHub Actions |
| **Scale** | Org spanning 330+ Apex classes, 80+ Lightning Web Components, 240+ automated flows and 60+ custom objects |
| **Performance** | Bulk-safe trigger and flow patterns tested against 200+ record batches; queueable callouts to keep external API load off the transaction path |
| **Security** | Field-level security deployed alongside every new field, permission-set-driven access, read-only integration boundaries for AI consumers |
| **Impact** | Sales, service and field teams work in purpose-built components — queue boards, availability pickers, hierarchy overviews — instead of generic list views |
| **Repository** | `Private` — enterprise codebase |

Working directly against production changes how you build. Every deployment runs as a validation first, every change lands through a reviewed pull request, and every automation is designed so that the failure mode is "nothing happens" rather than "wrong data everywhere".

</details>

<details>
<summary><b>Systems Integration Layer</b> — CRM, marketing, telephony and ERP in sync</summary>

<br/>

A set of bi-directional integrations connecting Salesforce with the surrounding business stack: marketing automation, HR, telephony and ERP.

| | |
|---|---|
| **Stack** | Apex REST/callouts, Named Credentials, Make.com scenarios, Brevo API, 3CX XAPI, HRWorks API, webhooks |
| **Scale** | Multiple always-on syncs covering contact data, campaign state, call data, employee records and order history |
| **Performance** | Event-driven rather than polling wherever the source supports it; batched writes and guarded retries on the rest |
| **Security** | Named-credential-based auth with no secrets in code or metadata, scoped API users, defensive validation on inbound payloads |
| **Impact** | One source of truth per data domain — marketing segments, call outcomes and order data resolve to the same records the sales team works in |
| **Repository** | `Private` — enterprise codebase |

The hard part of integration is never the happy path. Most of the engineering here is in the edge cases: negative call durations from a telephony provider, CRLF characters breaking downstream address fields, email changes that silently orphan a contact. Each one is now a guard with a documented reason.

</details>

<details>
<summary><b>Landing Page Build Pipeline</b> — design-system-driven page delivery</summary>

<br/>

A build workflow that turns structured source files into importable Oxygen Builder page definitions, so landing pages are versioned, diffable and reproducible instead of hand-assembled in a visual editor.

| | |
|---|---|
| **Stack** | Python build scripts, JSON page definitions, Oxygen Builder, WordPress, GA4, consent-aware tag management |
| **Scale** | Multiple campaign landing pages generated from a shared brand design system |
| **Performance** | Native builder elements over embedded code blocks, mobile-first breakpoints validated through headless rendering |
| **Security** | Consent-gated tracking — marketing tags fire only after opt-in, verified against the live consent manager |
| **Impact** | Page changes become code review instead of clicking; brand rules (typography, colour, CTA treatment) are enforced by the generator |
| **Repository** | `Private` — client work |

Visual builders are excellent for the last 10 % and terrible for the first 90 %. Generating the page structure from source keeps the layout consistent across campaigns while leaving the fine-tuning where designers actually want it.

</details>
